# Прогноз цен на недвижимость в России

Оценка рыночной стоимости квартир на вторичном рынке Москвы и
Санкт-Петербурга по реальным объявлениям с restate.ru. Пользователь вводит
параметры квартиры (город, площадь, этаж, тип дома) и получает точечную
оценку цены и оценочный диапазон.

**Данные**: 9 720 объявлений после очистки (собрано 9 839), Москва и
Санкт-Петербург, restate.ru, август 2026. У 92% есть координаты; по ним и
объектам OpenStreetMap (метро, школы, парки и т.д.) считаются геопризнаки.

**Процесс**: сбор данных → координаты и OSM POI → проверка качества →
признаки → разбиение **по домам** (объявления одного дома целиком в одну
часть) → XGBoost → FastAPI + Streamlit.

**Рабочая модель**: XGBoost + 18 геопризнаков OSM. Оценка на строгом
holdout (1 851 объявление, ни один дом не попадает в обе части):

| Метрика | Без geo | **С geo (рабочая)** |
|---|---:|---:|
| MAE | 6 519 591 ₽ | **5 909 113 ₽** |
| RMSE | 11 555 010 ₽ | **10 198 551 ₽** |
| R² | 0,641 | **0,720** |
| MAPE | 26,8% | **23,8%** |

Лучший простой базовый вариант (медианная цена за м² по городу и категории)
даёт MAE ≈ 7,83 млн ₽ — модель ниже примерно на **24,5%**.

**Честно**: это цена объявления, а не цена сделки; модель покрывает только
2 города; на двух маленьких категориях (дома, комнаты) модель заведомо менее
надёжна и явно сообщает об этом через API; на объявлениях без координат
средняя ошибка выше — подробности в разделе «Ограничения».

## Зачем этот проект

Можно ли по базовым параметрам квартиры (город, площадь, этаж, тип дома,
категория) получить быструю ориентировочную оценку рыночной цены? Учебный
проект, но данные и весь процесс обработки — настоящие, не синтетика.

## Данные

- **Источник**: restate.ru, публичные страницы поиска — HTML-парсинг с
  задержками и повторными попытками. ЦИАН (`src/data_collection/cian_scraper.py`)
  сейчас недоступен из-за CAPTCHA и оставлен в коде как резервный вариант.
- **Масштаб**: 9 839 собранных объявлений → 9 720 после очистки и удаления
  дубликатов — Москва (4 931), Санкт-Петербург (4 789), 7 категорий (студии,
  1–3-комнатные, новостройки, комнаты, дома/коттеджи).
- **Координаты**: страница поиска даёт только город, но у каждого объявления
  есть своя страница с точкой на карте (`data-lat`/`data-lng`).
  `scripts/enrich_coordinates.py` обходит их по одной с задержкой и кэшем —
  координаты получили 9 070 объявлений (92,2%), остальные остаются в выборке
  с признаком `has_coordinates = 0`.
- **Инфраструктура**: из OpenStreetMap (экстракты Geofabrik по Центральному и
  Северо-Западному ФО, разбор через `pyrosm`) —
  `scripts/prepare_osm_poi.py` собирает `data/external/osm_poi.csv`: 27 539
  объектов семи типов (метро, ж/д станции, школы, детсады, поликлиники/
  больницы, супермаркеты, парки). Данные © OpenStreetMap contributors, ODbL.
- **Проверки качества**: диапазонные фильтры на площадь/цену/этаж, точное
  удаление дубликатов по URL, отдельное обнаружение похожих объявлений
  (совпадающий адрес+комнаты+этаж, цена и площадь в пределах 2%) — такие
  объявления не удаляются автоматически, а учитываются при разбиении на
  обучающую и тестовую выборку (см. ниже).
- **Известные ограничения выборки**: район в явном виде не собирается; год
  постройки почти всегда отсутствует на страницах поиска, поэтому признак
  «возраст здания» фактически не несёт сигнала; у 7,8% объявлений нет
  координат.

Полная схема данных — в [`DATA_CARD.md`](DATA_CARD.md).

## Модель

**Таргет**: логарифм цены `log1p(price)`, обратное преобразование при
инференсе. XGBoost, гиперпараметры подобраны через Optuna по протоколу
обучение → GroupKFold кросс-валидация на train → выбор → один финальный
прогон на отложенной выборке (holdout ни разу не участвует в подборе).

**Разбиение — не случайное.** При обычном случайном разбиении 37,5% групп
похожих объявлений попадали одновременно в train и test. Рабочая оценка идёт
по ещё более строгому разбиению — **по домам** (все объявления с одной
координатой в одну часть), см. «Геопризнаки». Все метрики в этом разделе и в
`MODEL_CARD.md` — на этом location holdout.

**Заполнение пропусков — тоже только по обучающей выборке.** У части
объявлений отсутствуют число комнат/этаж/этажность (структурно — площадка
не публикует эти поля для части категорий, см. ниже). Пропуски заполняются
медианой по городу, посчитанной только на обучающей части после разбиения.

Простые базовые варианты для сравнения (тот же location holdout, статистики
только по train):

| Подход | MAE | R² |
|---|---:|---:|
| Глобальная медиана | 12 687 933 ₽ | −0,10 |
| Медиана по городу | 12 443 032 ₽ | −0,11 |
| Цена/м² × площадь (глобально) | 9 246 789 ₽ | 0,41 |
| Цена/м² × площадь (по городу и категории) | 7 827 916 ₽ | 0,54 |
| **Модель (XGBoost + geo)** | **5 909 113 ₽** | **0,72** |

**Где модель ошибается больше всего**: дороже объект — больше абсолютная
ошибка (верхняя ценовая треть MAE ≈ 11,3 млн ₽ против ≈ 2,4 млн ₽ у нижней);
категории «дома/коттеджи» и «комнаты» (по ~30 объектов на holdout) заметно
слабее остальных — структурная причина, не размер выборки: источник не
публикует число комнат для этих категорий (и этаж/этажность — для домов).
`POST /predict` принимает необязательное поле `property_category`; для этих
двух категорий ответ возвращает `prediction_reliability: "limited_data"`.

Полный разбор метрик и сегментов — [`MODEL_CARD.md`](MODEL_CARD.md).

## Геопризнаки (OpenStreetMap)

По координатам объявления и объектам из `data/external/osm_poi.csv`
считаются 18 признаков (`src/features/geo_features.py`):

- расстояние до ближайшего объекта каждого типа — метро, ж/д станция,
  школа, детсад, поликлиника, супермаркет, парк — по формуле гаверсинуса
  (`BallTree`, метрика `haversine`), а не по разнице градусов;
- количество объектов в радиусе 500 м и 1000 м для супермаркетов, школ,
  детсадов, поликлиник, парков, станций метро;
- флаг `has_coordinates`.

Категория `metro` в OSM — вперемешку станционные точки и входы (≈1556
объектов в Москве на ~260 станций). Поэтому каждая категория пространственно
схлопывается до объектного уровня: 371 станция метро в Москве, 83 — в СПб.

POI ищутся только внутри своего города. Сырые `latitude`/`longitude` в
модель не входят — только 18 производных признаков. Объявления без координат
(7,8%) сохраняются: расстояния — заглушка, счётчики — 0, `has_coordinates=0`.

Геопризнаки — внешний справочный джойн (ничего не обучается на объявлениях),
считаются до разбиения, leakage-safe схема не нарушается.

### Разбиение: по домам

Из-за address-level геокодирования многие объявления в одном доме получают
одну точку. Обычное разбиение «по похожим объявлениям» разводит только
повторные публикации одного объявления, но разные квартиры одного дома
могут попасть по обе стороны — модель частично «узнаёт» дом.

Основное разбиение — **по домам** (`build_location_groups`): все объявления с
одной округлённой координатой (или взаимно похожие) идут только в одну
часть. 9720 объявлений → 2609 «домов».

Схема: DEV (80%, 7869) → 4-fold GroupKFold для подбора гиперпараметров →
FINAL HOLDOUT (20%, 1851) — одна финальная оценка. Holdout ни разу не
участвует в тюнинге. Seed 42, одно разбиение для всех кандидатов. Проверка
(`scripts/verify_split_leakage.py`): 0 групп похожих объявлений и 0 из 1867
«домовых» кластеров попадают в обе части.

### Результат — FINAL location holdout (1851 объявление)

| Кандидат | Признаки | MAE | RMSE | R² | MAPE |
|---|---|---:|---:|---:|---:|
| production_pre_geo | без geo | 6 519 591 ₽ | 11 555 010 ₽ | 0,641 | 26,8% |
| **geo (production-параметры)** | + geo | **5 909 113 ₽** | 10 198 551 ₽ | **0,720** | **23,8%** |
| geo (tuned-параметры) | + geo | 6 142 732 ₽ | 10 627 517 ₽ | 0,696 | 24,5% |

Прирост geo против pre-geo: **MAE −9,4%, MAPE −3,0 п.п., R² 0,64 → 0,72.**
Лучший простой baseline (цена/м² по городу и категории) даёт MAE ≈ 7,83 млн ₽
— geo-модель ниже примерно на **24,5%**. Тюнинг на новом разбиении (50 trials
Optuna) не улучшил уже используемые production-гиперпараметры — рабочая
модель берёт их + геопризнаки.

Оба города улучшаются (Москва 6,25 → 5,97 млн; СПб 6,86 → 5,83 млн), все
ценовые сегменты тоже. На объявлениях без координат средняя ошибка выше на
хвосте (маленькая выборка 160), но медиана и MAPE у geo-модели там лучше.

Для справки, оптимистичное разбиение «по похожим объявлениям» (НЕ основная
оценка, завышает из-за соседей по дому): geo MAE 2 713 581 ₽, R² 0,889.

`nearest_metro_station_distance_m` — 4-й признак по permutation importance на
holdout; из 15 важнейших 6 — геопризнаки (`parks_1000m`, `hospitals_1000m`,
`nearest_rail_station_distance_m`, расстояния до парка и детсада).

### Продвижение — geo-модель переведена в рабочие

`scripts/geo_promotion_gate.py` → **PROMOTION_READY (9/9)**, после чего
geo-модель промоутнута:

```bash
python scripts/run_model_training_real.py --model xgboost --split-strategy location --params-from-manifest
python scripts/promote_model.py --candidate models/<artifact>.pkl --dry-run
python scripts/promote_model.py --candidate models/<artifact>.pkl
```

`current_model.json` → `xgboost_20260909_112549.pkl` (`split_strategy:
location_grouped_80_20_random_state_42`, `geo_enabled`). Предыдущий pre-geo
артефакт сохранён; откат — `python scripts/promote_model.py --rollback`.

`promote_model.py` знает про геопризнаки (единый источник истины —
воспроизведение реального пайплайна), проверяет все 45 признаков, imputer,
провенанс. Geo-модель зависит от локального `data/external/osm_poi.csv`: без
файла API отдаёт понятную ошибку (503), дашборд — сообщение, а не тихо
деградирует; pre-geo модель OSM не требует.

### Геоданные и Git

- `data/external/osm_poi.csv` (~2 МБ, 27 539 объектов) и
  `osm_poi_manifest.json` **хранятся в Git** — этого достаточно, чтобы
  geo-модель работала сразу после `git clone`.
- Исходные PBF-экстракты OSM (`data/external/osm/*.osm.pbf`, ~1,5 ГБ) в Git
  **не хранятся**. Они нужны только чтобы пересобрать `osm_poi.csv`:
  `scripts/prepare_osm_poi.py` сам скачивает их с Geofabrik
  (`--rebuild` — пересобрать из уже скачанных, `--force` — перекачать).
  Обычный `prepare_osm_poi.py` — no-op, если `osm_poi.csv` уже на месте.
- Без `osm_poi.csv` geo-модель **намеренно** недоступна (API → 503, дашборд →
  сообщение). Это fail-closed поведение, а не баг: лучше явная ошибка, чем
  тихий прогноз с нулевыми геопризнаками.

## Рабочая модель

`models/current_model.json` → **XGBoost + 18 геопризнаков OSM**
(`xgboost_20260909_112549.pkl`), обучен на реальных данных Restate, оценён
на строгом location holdout. API и дашборд показывают состояние через
`GET /model-info` (`geo_enabled`, `geo_poi_available`, `coordinate_coverage`,
`osm_poi_manifest`). Переключение модели в рабочую — отдельная явная команда,
никогда не побочный эффект обучения:

```bash
python scripts/promote_model.py --candidate models/<artifact>.pkl   # промоушен
python scripts/promote_model.py --rollback                          # откат на предыдущую
```

Предыдущий pre-geo артефакт (`xgboost_20260827_131014.pkl`) физически
сохранён; история переключений — в `reports/promotion_log.jsonl`.

Перед записью в `current_model.json` скрипт проверяет: версию схемы
признаков, точный список и порядок всех признаков (включая 18 геопризнаков —
единый источник истины, воспроизведение реального пайплайна), наличие
обученного imputer, адекватность метрик, отсутствие абсолютных путей — и
отказывается писать что-либо, если хоть одна проверка не прошла.

**Откат**: предыдущий артефакт не удаляется при переключении
(`current_model.json` хранит `previous_current_filename`). Откат — та же
команда с указанием предыдущего файла.

## Архитектура

```
restate.ru → скрейпер → data/raw/restate/*.jsonl
                              │
                              ▼
                  data/interim/restate_<city>_listings.csv
                              │
      очистка + макроэкономические признаки + геопризнаки (OSM POI)
                              │
                              ▼
              data/processed/real_estate_cleaned.csv
                              │
              разбиение по домам → DEV / FINAL HOLDOUT
                              │
      заполнение пропусков (только по train) → подготовка признаков
                              │
                    подбор гиперпараметров (DEV CV only) → XGBoost + geo
                              │
              scripts/promote_model.py (явная, отдельная команда)
                              │
                              ▼
                     models/current_model.json
                              │
                  ┌───────────┴────────────┐
                  │                        │
           FastAPI (:8000)         Streamlit (:8501)
```

`Predictor` переключается в демо-режим на эвристических ценах, если в
`models/` нет обученной модели.

Рабочая модель (`models/xgboost_20260909_112549.pkl`) и таблица OSM POI
(`data/external/osm_poi.csv`, ~2 МБ) уже в репозитории — после `git clone`
дополнительно готовить данные не нужно.

Windows / PowerShell:

```powershell
cd projects\real-estate-price-prediction
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt -r requirements-dev.txt
```

macOS / Linux — то же, но `python3 -m venv .venv && source .venv/bin/activate`.

```powershell
uvicorn api.main:app --reload --port 8000
```

## Ограничения

- **Только 2 города** реально покрыты данными (только для них есть OSM POI).
- **Около 8% объявлений без координат**: у них геопризнаки — заглушка,
  `has_coordinates=0`. На этой подвыборке средняя MAE у geo-модели выше
  (хвост на ~160 объектах holdout), хотя медианная ошибка и MAPE лучше.
- **Координаты address-level**: объявления в одном доме имеют одну точку,
  поэтому оптимистичное разбиение переоценивает прирост; честная оценка — по
  разбиению «по домам».
- **`room_sale` (26 объектов на holdout, слабый R²) и `cottages_sale`** —
  low-support сегменты: источник не публикует комнаты/этаж. API возвращает
  `prediction_reliability: "limited_data"`.
- **Дорогие объекты**: абсолютная ошибка заметно выше (верхняя ценовая треть
  MAE ≈ 11,3 млн ₽ против ≈ 2,4 млн ₽ у нижней).
- **Geo-инференс зависит от `data/external/osm_poi.csv`** и актуальности
  OSM-снимка. Снимок фиксируется в метаданных артефакта (`osm_poi_manifest`).
- **Возраст здания и макропоказатели** на реальных данных почти не
  варьируются: год постройки почти всегда отсутствует в источнике.
- **Категории «дома/коттеджи» и «комнаты»** — маленькие структурно слабые
  сегменты: источник не публикует число комнат для них (и этаж/этажность —
  для домов). Раскрывается через `prediction_reliability` в ответе `/predict`.
- **Прогноз — это цена объявления, а не независимая рыночная оценка**:
  модель учится на заявленных продавцами ценах, а не на цене сделки.
